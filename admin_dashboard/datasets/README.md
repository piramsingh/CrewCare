# datasets

Two CSVs. One describes the network, the other is the worker-report corpus.
Both are read by `../admin_dashboard_model/` as `APP_DIR.parent / "datasets"`,
so this folder has to stay a sibling of the model folder.

| file | rows | what it is |
|---|---|---|
| `nyc_subway_station_spine.csv` | 496 | every subway station, with what the models need to score it |
| `worker_complaints.csv` | 449 | the synthetic worker-report corpus |

---

## nyc_subway_station_spine.csv

One row per GTFS stop, 34 columns, built from MTA Subway Stations (`39hk-dx4f`)
and Subway Entrances and Exits (`i9wp-a4ja`) on NYS Open Data.

**Keys.** `gtfs_stop_id` is the primary key and the id every other part of the
system uses. `complex_id` groups the platforms of one station — 34 St-Herald Sq
is two rows, `R17` (N Q R W) and `D17` (B D F M), sharing complex `607`. 35
complexes span more than one stop.

**Never join on `stop_name`.** 76 names are used by more than one station,
covering 193 of the 496 rows. "86 St" is six separate stations in six separate
complexes — R, N, C/B, 1, 4/5/6 and Q, across Brooklyn and Manhattan — and they
are not interchangeable.

The eleven columns the models actually read:

| column | used for |
|---|---|
| `gtfs_stop_id` | the key |
| `complex_id` | collapsing platforms to one station in ranked lists |
| `stop_name`, `borough`, `daytime_routes` | labels |
| `structure` | enclosure → ventilation rate (`Subway`, `Elevated`, `Open Cut`, `Viaduct`, `At Grade`, `Embankment`) |
| `route_count` | service level → how much brake dust and heat the trains generate |
| `street_latitude`, `street_longitude` | which Open-Meteo grid cell the station sits in, and where it plots on the map |
| `latitude`, `longitude` | platform coordinates, the fallback when street coordinates are missing |

Street coordinates are preferred over platform coordinates because the modelled
input is ambient outdoor air — what is above the station, not what is in the
tunnel.

The remaining columns (ADA status, entrance counts and spread, division, line,
CBD flag, WKT geometry) are carried for downstream use and are not read by the
models.

## worker_complaints.csv

**Synthetic. These are not reports from real workers** and are not evidence
about any real station. Every row carries `demo`. They exist so the dashboard
has a network-scale picture to draw.

449 records across 196 stations over twelve weeks, generated by
`../admin_dashboard_model/complaints.py`, weighted so enclosed platforms skew
to heat and dust while open-air ones skew to noise and structure.

| column | notes |
|---|---|
| `id` | opaque record id |
| `station_id` | joins to the spine's `gtfs_stop_id` |
| `days_ago` | days before the export date — **the field that matters, see below** |
| `reported_on` | ISO date, as of the export |
| `category` | one of seven: dust/air quality, heat, damp/mould/standing water, ventilation, fumes, noise, other |
| `severity` | `Noticeable`, `Affects my work`, `Made me unwell` |
| `text` | the free-text report |
| `demo` | always `true` here |

### Why `days_ago` exists

`complaints.py` re-anchors every date to today on load. A frozen `reported_on`
column would age: a month after the export, a dashboard showing "the last 30
days" would be empty, and the corpus exists to give it something to show.
Re-anchoring keeps the shape — which station, which concern, how long ago — and
slides the window with whoever opens it.

So `reported_on` is a snapshot of the export date; `days_ago` is the source of
truth.

### Regenerating

```bash
cd ../admin_dashboard_model
python complaints.py --export      # redraw the corpus and rewrite the CSV
```

Running the app does **not** regenerate it, so a checkout always shows the
records that are in version control.

### What is deliberately absent

The runtime store (`admin_dashboard_model/complaints.json`) is gitignored, so
real submissions never reach a public repo. The record shape itself is the
privacy design: no name, no employee number, no device or session id, and a
date rather than a timestamp — a precise submission time plus a roster
identifies who was on duty. There is no edit or delete by the submitter,
because that needs a token tying a person to a record, which is exactly what is
not stored.
